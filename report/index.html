致命缺陷

这三个问题里，第 1 个最要命——它意味着你后续做的任何改进，都送不到用户手里。

严重
Service Worker 缓存永不更新

原版是 cache-first + 硬编码版本号 shishi-v3。用户第一次访问后，浏览器就永远拿缓存，你发了新版他还是看旧的。改为 stale-while-revalidate：秒开 + 后台静默拉新。

严重
蛋白质目标失控（可达 44% 热量）

90kg 用户选 2.4g/kg = 216g 蛋白 = 792 kcal。若在减脂期（目标 1800 kcal），蛋白质 alone 就占 44%，碳水被挤到几乎没有。已加 35% 上限——这是运动营养学中有文献依据的阈值。

严重
热量目标可低于基础代谢

小个子女性选「减脂 −500」会算出低于 BMR 的目标，长期执行有害健康，产品却没有任何拦截。已加 BMR×1.1 下限保护。

中等
emoji 当图标

🥗📊🥬📷 在 iOS / Android / Windows 上渲染差异极大——有的彩色、有的方框、有的基线错位。已全部替换为 24 个内联 SVG，统一 stroke-width:1.8 线宽。

中等
原生 prompt / confirm 弹窗

记录吃掉食物时弹出浏览器的丑陋原生对话框，在 PWA 独立窗口模式下体验尤其割裂。已全部换成自建底部抽屉。

中等
库存这个唯一差异点被浪费

「库存管家」是本品类唯一的差异功能，但原版把 20 样食材平铺成一长条，没有分组、没有余量提醒——用户根本感受不到它和别的 App 有什么不同。已做分类分组 + 低量提醒条。

中等
无输入校验

年龄能填 999、体重能填 0，calc() 直接产出垃圾数字。已加合理区间校验（年龄 10–100、身高 100–250、体重 25–300、单次运动 ≤600 分钟）。

额外发现（只有真实浏览器才能抓到）
组装完成后，我在真实 Chromium 里截图，发现首屏是完全空白的—— 因为 #tab-today 没有 .on 类，而 .tab{display:none}。
诡异的是：DOM stub 测试全绿（元素存在、内容长度 635、渲染函数正常返回）。 这是一个 纯 DOM 测试永远抓不到、只有像素级渲染才能发现的 bug。已修复。

最关键的一个细节

抽屉里输入克重时，下方实时显示这一口吃进去多少营养：

≈ 133 kcal · 蛋白 19.4 · 脂肪 5.0 · 碳水 2.5 g

原版没有这个。但用户真正想知道的就是「我吃这 150g 鸡胸肉到底摄入了多少」。它把一次「填数字」变成了「有反馈的决策」——这是让产品从「能用」变成「好用」的地方。

第二轮 · 把「库存」从列表变成系统

第一轮只是让库存能看，第二轮让它会算。核心判断：纯记录型 App 用户记两天就懒得记了，因为它不还嘴。只有让它主动产出「还够吃几天」「该买什么」「今天差多少蛋白」，用户才有理由每天回来。

新增
消耗速度预测

「还剩 620g」是没用的信息，「还能吃 6 天」才是有用的。按近 7 天实际消耗算日均，预测每样食材的剩余天数，并汇总出整柜续航。

新增
自动采购清单

从「提醒你库存低了」升级到「告诉你要买多少」。按真实消耗速度把低量食材补足到够吃 7 天，一键生成、可复制。

新增
缺口分析 + 蛋白补足建议

对比目标与已摄入，算出还差多少。然后从你自己的库存里按蛋白密度挑最优解：「吃 1150g 希腊酸奶 可补足蛋白」。这是同类产品都没有的能力——它把「知道差多少」变成了「知道该吃什么」。

新增
每项自定义提醒线 + 14 天消耗柱图

鸡蛋剩 25g 该买、巴旦木剩 60g 不用买——一个全局阈值管不了所有食材。每项可设独立提醒线，点开还能看自己的真实消耗曲线。

关键设计：样本不足时不给预测
消耗预测最容易犯的错是「拿一天数据就开始预测」。所以 dailyBurn() 在 有记录的天数少于 2 天时返回 null，界面显示「待记录」而不是一个假数字。

理由：如果昨天只记了一次「吃了 500g 鸡胸肉」，算出来日均 500g、预测「还剩 1 天」——这是纯噪声， 会直接误导采购决策。宁可显示「还不知道」，也不要显示一个错的。

第三轮 · 首屏信息层级

第二轮做完后截图发现两个真问题：库存页把「手动添加食物」表单放在最上面，用户每天进来第一眼看到的是一张填表框；而本轮新增的「今日还差」卡被挤到了首屏以下——最难做的功能藏得最深。

→手动添加改为 <details> 折叠，移到所有汇总卡之后（添加是低频操作，看库存是高频操作）已修正
→压缩概览卡内边距与行高，为主信息腾出首屏空间已修正
→新增溢出提示：概览卡 / 缺口卡不在首屏时测试直接报错已加断言

修正前后首屏卡片位置：

修正后 库存总计 @104 · 今日还差 @263 · 我的库存 @473 —— 全部在首屏内

第四轮 · 习惯层（连续记录 + 体重趋势）

库存管家解决了「这个工具能算什么」，但没解决「用户为什么明天还会打开」。要让人回来，得给一个每天看一眼就知道自己状态的东西。

新增
连续记录天数

两个克制的设计决定：① 今天还没记不算断——当天还没结束，这时归零会让用户觉得被惩罚；② 空数组不算记录。另外同时显示「本月天数」和「历史最长连续」，只有当前 streak 会让人焦虑（断了就全没了），加上积累型的指标后断了也不归零。

新增
体重趋势：看斜率，不看单日

体重每天波动 1–2kg 是正常的（水分、食物残留），所以显示单日变化没有意义。改用最小二乘拟合斜率，输出 kg/周——这是营养学界描述体重变化的标准单位，也天然过滤掉了日间噪声。少于 2 个数据点直接返回 null，不拿单点瞎画趋势线。

一个图标引发的教训
连续记录卡用了一个火焰图标，但渲染出来是一个水滴——原路径顶端是对称圆滑的，没有火焰该有的尖。 光看 path 字符串完全判断不出来。

解法：写一个临时页面把 6 个候选路径用 76px 并排渲染对比，再单独预览 38px 实际尺寸下的效果，最后才选中正确的那个。
图标是图形，不是代码——必须渲染出来看。

GitHub 调研：采纳与否决

按「上 GitHub 找自己没有的 / 可优化的」要求调研了同类项目，其中三个有参考价值：

✓brandonp2412/FitBook（174★）7000+ 食物库（源自 CORGIS 数据集）食物库扩充方向
✓LowCarbCheck/openplate（57★）自托管 + 本地优先 + BYOK定位验证
✓garettie/eatlog 体重趋势线（看斜率不看单日）已落地
明确否决：接入 OpenFoodFacts API
调研时看到 FitBook / openplate 都用它做条形码查询，看起来很香（免费、百万条数据）。但实测中文数据后否决了：

搜索「全麦面包」→ 仅 1 条命中，且该条 energy-kcal_100g 为 null
搜索「鸡胸肉」 → 7 条命中，全是包装即食鸡胸肉，无生鲜数据

开放食物库的中文覆盖以进口包装食品为主，中国用户买菜场景（生鲜、散装）基本查不到。 加进去的代价是引入网络依赖和一次 API 调用，换来的却是不可靠结果—— 这会让用户觉得「识别不准」，伤害的是核心信任。不如把 87 条内置数据做扎实。

原版是「绿→青渐变 + 高饱和」，属于典型的 AI 生成感设计语言。新版的思路是去掉所有装饰性表达：渐变改中性表面 + 一条 hairline；强调色从亮绿 #16a34a 换成松花绿——中国传统色，饱和度和明度都低，更接近真实植物的颜色，用在数据可视化上不刺眼。

骨白#faf8f5
松花绿#3B7A57
墨#2b2a27
蛋白#4a6fa5
脂肪#c8873f
碳水#7c5c9e

其他细节：圆角从全 999px 胶囊改为 8/12/16/20 四级；数字统一 tabular-nums 等宽（数值不跳动）；阴影几乎看不见（0 1px 2px rgba(43,42,39,.03)），只提供层次。

教训一：DOM stub 不能替代真实浏览器
那个「首屏空白」的 bug，在 stub 里所有断言都是绿的（元素存在、内容非空）， 只有 Playwright 截图才发现父容器是 display:none。 所以浏览器渲染测试是必跑项，不是可选项。

教训二：改了代码但行为没变，先确认文件进了构建产物
改火焰图标时先改了 _build/icons.js，重跑组装脚本，重新截图——完全没变。 原来是组装脚本只拼 new.css + new_body.html + new_app.js， icons.js 是重构残骸，从来没被引用。 grep 一下产物文件里有没有刚写的字符串，两秒就能确认。

第五轮 · 训练自定义 + 装到手机

两条来自真实使用的反馈，都指向同一个问题：功能做了，但用户够不到。

训练
「项目都是固定的，我跑了 5 公里你要给我具体的消耗」

拆掉 20 项固定 MET 菜单，改成 距离法 / 时长法 / 心率法 三选一。 关键论据：同距离的奔跑消耗与配速基本无关，所以问距离而不是配速 —— 70kg 跑 5km = 363 kcal，且 25 分钟与 40 分钟结果相同。

营养
训练日和休息日该吃的不一样

两套目标：训练日 = TDEE + 实际运动消耗，休息日 = TDEE + 调整。 蛋白质按强度上调，膳食纤维新增为追踪项（IOM 标准 + 训练日 +5g）。 修掉一个 414 kcal 的窟窿：脂肪取 28/30%、碳水补足余量，宏量回算恒等于目标。

安装
「手机上怎么下载？浏览器能打开，但没有下载」

识食是 PWA，故意不做安装包。但「添加到主屏幕」这个入口在不同浏览器里 叫法位置全不一样。所以主动捕获 beforeinstallprompt， 首页横幅点一下就弹系统原生安装框；iOS 没有这个 API，降级成图文步骤。

这一轮最值得记的一条
没有任何算法或逻辑 bug，代码一直是正确的。缺的只是「用户不知道去哪儿点」。 而这类问题单元测试发现不了——测试里我们总是直接调函数、直接给元素， 真实用户却要先找到那个元素。

所以凡是「用户第一次要做某件事」的路径（安装、初始化、导入数据）， 都值得像功能一样认真设计一遍入口。

关于见效时间，说实话
被动路径起量慢，这是结构性的，不是执行问题：开源项目冷启动通常 3–6 个月才有稳定自然流量； Product Hunt / HN 单次爆发可能带来几百访问，但留存靠产品本身。

能加速的事：把「设计决策」写出来（比如为什么数据不够就不给预测）。 技术社区对「一个具体的、可争论的决定」反应，远好于「一个新功能」。
